Risque de décalage horaire sur les jackpots
Le formulaire jackpot utilise un datetime-local, puis transmet une heure sans fuseau au serveur :
[jackpot-editor.tsx (line 35)](/C:/Users/MISHOW/Documents/LastChance/Lastchance/src/components/dashboard/jackpot-editor.tsx:35)
[jackpot.ts (line 77)](/C:/Users/MISHOW/Documents/LastChance/Lastchance/src/lib/validations/jackpot.ts:77)
Une saisie 18:00 faite pour Paris peut être interprétée comme 18:00 UTC sur le serveur, donc déclenchée à 20:00 en été. D’autres formulaires convertissent depuis le fuseau du navigateur, mais cela reste faux si le commerçant voyage.
À faire :
interpréter toutes les dates avec organization.timezone ;
créer une fonction commune zonedDateTimeToIso ;
afficher explicitement « Heure de Paris » dans les formulaires ;
tester le passage heure d’été/hiver ;
traiter les heures inexistantes ou ambiguës lors des changements DST.
Cela doit couvrir tirages, verrouillages, débuts, fins et automatisations.

Le chantier technique le plus important : unifier les récompenses
Vous avez maintenant au moins neuf sources de récompenses et huit mécanismes de rédemption distincts. Cela explique le bug des pronostics et créera d’autres incohérences : expiration disponible dans un module mais pas un autre, Wallet sur la roue mais pas sur le quiz, statistiques incomplètes, emails différents, etc.
Je recommande un registre commun :
reward_issuances

- organization_id
- player_id
- source_type
- source_id
- experience_id
- reward_definition_id
- code
- label
- metadata
- issued_at
- expires_at
- redeemed_at
- redeemed_by
- cancelled_at
- basket_amount_cents
- wallet_status
Puis un seul moteur :
redeem_reward_by_code(code, organization, cashier, basket_amount)
Il doit prendre en charge :
contrôle de l’organisation ;
contrôle du rôle ;
expiration ;
annulation ;
rédemption concurrente ;
décrémentation/restauration de stock ;
journal d’audit ;
automatisations ;
Wallet ;
analytics.
La migration doit être progressive : toutes les nouvelles récompenses passent par ce registre, puis les anciennes tables sont adaptées ou réconciliées. Il ne faut pas tenter une réécriture globale en une fois.
Unifier l’identité joueur
Le projet dépose aujourd’hui des cookies différents selon le programme ou l’expérience : fidélité, chasse, jackpot, calendrier, quiz, événement, pronostics, etc. Comme certains noms contiennent un UUID, un joueur très actif peut finir avec des dizaines de cookies. Cela peut entraîner éviction silencieuse, perte de progression ou en-têtes HTTP trop volumineux.
Conséquences actuelles :
progression perdue si le navigateur est nettoyé ;
quasiment aucune récupération multi-appareils ;
difficulté à reconnaître les visites répétées ;
impossibilité de construire correctement des missions entre jeux ;
limitations anti-fraude incohérentes.
Je recommande :
un seul cookie opaque lc-player ;
une table centrale players ;
des player_devices avec rotation des jetons ;
des adhésions séparées par organisation et expérience ;
une liaison email facultative par magic link ;
une récupération de progression ;
une séparation stricte entre organisations ;
du consentement explicite avant tout rapprochement nominatif.
C’est la dépendance indispensable avant d’ajouter badges, collections, missions et progression générale.

Sécurité et équité à ne pas oublier
Je n’ai pas identifié de nouvelle faille critique inter-organisations dans cette lecture, mais certains sujets deviennent importants si les lots ont une vraie valeur :
les événements et quiz restent sensibles au multi-cookie/Sybil ;
certains mini-jeux de réflexe transmettent des résultats calculés côté client ;

Avant d’autoriser des lots importants :
Turnstile à la première inscription ;
temps de départ signé par le serveur ;
détection des scores physiquement impossibles ;
limites par appareil, compte et campagne ;
alias générés ou filtre de grossièretés ;
bannissement/modération pendant les événements ;
règle économique centrale sur le stock et la valeur maximale distribuable.

Ce que je développerais ensuite
Je ne développerais pas immédiatement un autre jeu autonome. La meilleure extension, dans la continuité de votre imagination, est une couche de méta-progression.
Idée	Intérêt	Dépendances
Missions multi-jeux	« Scanner 3 fois, réussir un quiz, parrainer un ami »	Identité et analytics communs
Collections et badges	Objets saisonniers, équipes, cartes, trophées	Identité commune
Clés et coffres	Une action donne une clé, plusieurs clés ouvrent un coffre	Registre de récompenses
Pass saisonnier	Progression sur plusieurs semaines avec paliers	Missions + récompenses
Parcours personnalisés	Proposer le jeu suivant selon l’historique	Analytics + consentement
Validation d’achat	Débloquer une tentative après ticket ou passage caisse	POS/API/ticket
Défis entre équipes	Magasins, écoles, événements, supporters	Live + identité
Campagnes réseau	Mission entre plusieurs établissements partenaires	Isolation et consentement solides

La meilleure idée produit est probablement :
Un QR n’ouvre plus simplement un jeu. Il fait progresser le joueur dans une mission, une collection ou une saison.

Cela transforme les expériences existantes en composants réutilisables et augmente la fréquence de retour, sans devoir inventer constamment de nouveaux jeux.
