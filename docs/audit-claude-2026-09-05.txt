  [LANE] Rapport d'une lane dont j'ai lu le raisonnement et les références

Et l'une de ces deux qualifications :
  CONFIRMÉ    — le défaut existe dans le code tel qu'il est aujourd'hui.
  À VÉRIFIER  — indice sérieux, preuve incomplète ; ce qui manque est dit.

DEUX AFFIRMATIONS DE LANE ONT ÉTÉ ÉCARTÉES APRÈS VÉRIFICATION, et elles ne
figurent donc pas dans ce rapport :
  - un SSRF supposé à l'envoi des webhooks sortants : en réalité fermé.
    postSafeWebhook (src/lib/webhook-url.ts:120-160) re-résout le DNS,
    revalide les IP, ÉPINGLE l'adresse, conserve servername pour TLS et ne
    suit aucune redirection. La fenêtre de DNS rebinding est fermée.
  - des codes de retrait à 4 caractères, supposés énumérables : aucun
    générateur n'en produit. Les randomCode(4) du dépôt sont des suffixes
    de slug (auth.ts:203, jackpot.ts:373), jamais un code de gain. Les
    codes de gain font 8 symboles sur 32 (~2^40), et le modulo n'est pas
    biaisé (256 est divisible par 32), côté SQL comme côté TypeScript.


=========================================================================
1. ÉTAT GÉNÉRAL DU PROJET
=========================================================================

Le cœur du produit — le parcours de jeu et l'attribution des lots — est
sain, et nettement au-dessus de la moyenne d'un SaaS à ce stade. Ce n'est
pas une politesse : le chemin a été lu ligne à ligne.

CE QUI A ÉTÉ VÉRIFIÉ ET TIENT :

  - L'AUTORITÉ EST À LA BASE, partout où ça compte. Le tirage n'est pas en
    TypeScript : perform_atomic_spin (PL/pgSQL, security definer,
    search_path figé, 20260927120000_boucle_joueur_gain.sql:138). Une
    seule transaction porte éligibilité + tirage + réservation de stock +
    insertion, sérialisée par joueur via
    pg_advisory_xact_lock(wheel_id || ':' || player_key).

  - ALÉA CRYPTOGRAPHIQUE : extensions.gen_random_bytes(4), pas random().
    Biais de modulo négligeable aux ordres de grandeur réels (v_total /
    2^32).

  - PAS DE SUR-ÉMISSION DU DERNIER LOT. Le décrément est un CAS :
    update prizes set stock = stock - 1 where id = ... and stock > 0,
    avec re-tirage si la ligne a été prise (boucle, :279-281). En READ
    COMMITTED la seconde transaction bloque sur le verrou de ligne puis
    ré-évalue la condition sur la version à jour : elle ne trouve rien et
    reboucle. Vérifié aussi : les 12 autres sites de décrément portent
    tous « and stock > 0 », et prizes.stock a check (stock is null or
    stock >= 0) (00001_initial_schema.sql:74).

  - « UNE PARTIE PAR FENÊTRE » EST GARDÉE TROIS FOIS : verrou consultatif,
    test applicatif dans la RPC, et index unique partiel
    spins_one_per_window_idx (wheel_id, player_key, play_window_key)
    where play_window_key is not null (00019:150).

  - LE CLIENT NE CHOISIT RIEN. L'angle d'arrêt de la roue est DÉRIVÉ du
    prizeIndex renvoyé par le serveur, jamais l'inverse. weight et
    cost_cents ne quittent jamais le serveur : vérifié,
    src/lib/play-context.ts ne les sélectionne pas.

  - LE FUSEAU NE PEUT PAS ANNULER LA LIMITE. Piège cherché et fermé :
    organizations.timezone est « not null default 'Europe/Paris' »
    (00019:11). Un timezone NULL aurait rendu v_local_now NULL, donc
    v_window_start NULL, donc la garde de limite inopérante — ce n'est pas
    atteignable.

  - CHIFFRES DE CONTRÔLE : 147/147 tables avec RLS ; 417/417 fonctions
    SECURITY DEFINER avec search_path figé (invariant gardé en CI par
    supabase/tests/search_path_invariant.test.sql) ; 0 policy using(true) ;
    0 policy to anon/public sans prédicat tenant ; 1 seul grant à anon
    (tirer_ticket_or, mutante mais correctement gardée) ; 0 vulnérabilité
    npm sur 1221 dépendances cumulées ; 0 permissivité de build
    (ignoreBuildErrors et ignoreDuringBuilds absents, strict: true) ;
    0 secret en NEXT_PUBLIC_* ; pull_request_target absent des workflows ;
    0 continue-on-error ; EXPECTED_MIGRATION = 20261207120000, concordante
    et gardée par un test bloquant.

  - AUTRES SURFACES VÉRIFIÉES SAINES : signature Stripe (constructEvent,
    corps lu en text() avant parsing, api/stripe hors matcher du proxy) ;
    comparaisons à temps constant centralisées dans src/lib/timing-safe.ts,
    aucun === sur un secret ; les 11 crons protégés par le même garde
    fail-closed et tous idempotents ; Turnstile fail-closed en production
    avec action et hostname vérifiés ; redeem_by_code atomique (UPDATE
    unique avec redeemed_at is null, donc pas de double retrait) et scopée
    par organisation ; org_has_module_access DB-autoritaire, lève sur
    module inconnu au lieu de rendre false.

OÙ EST LE RISQUE, ALORS. À trois endroits, et aucun n'est la roue :

  1. Le lot local non commité (3 CRITIQUE). Il n'est pas en production,
     mais aucun de ces fichiers n'est dans .gitignore : un « git add . »
     les emporte.
  2. Deux jeux d'adresse où le client déclare sa propre victoire.
  3. Ce qui n'est PAS testé : la concurrence et les statistiques. Les deux
     invariants les plus critiques du produit ne sont gardés par rien, et
     l'un d'eux est gardé par un test qui vise le mauvais moteur — ce qui
     est pire qu'une absence, parce que ça ressemble à une couverture.

C1 — ÉCRITURE DE FICHIER À EMPLACEMENT ARBITRAIRE, SANS AUTHENTIFICATION
-------------------------------------------------------------------------
Fichier   : src/app/api/save-frame/route.ts:26-47   [LU] CONFIRMÉ
Zone      : export async function POST
Problème  : `index` arrive du corps JSON sans typage ni borne, est injecté
            dans `frame-${String(index).padStart(3,"0")}.webp`, puis passé
            à path.join(FRAMES_DIR, fileName). path.join normalise les
            segments « .. » : la traversée sort du répertoire.
Scénario  : POST /api/save-frame
            {"index":"../../../../tmp/pwn","data":"data:image/webp;base64,AAAA"}
            écrit des octets choisis hors de public/frames. Le suffixe
            .webp est forcé (donc pas d'exécution directe) mais
            l'emplacement et le contenu sont libres, y compris dans
            public/, servi depuis l'origine de l'application.
Aggravant : l.49 renvoie err.message brut => divulgation de chemins FS.
            Aucune borne de taille sur `data` => DoS mémoire/disque.
            Le GET (l.9-23) liste le répertoire.
Impact    : écrasement de fichiers, DoS disque, divulgation de chemins.
Cause     : concaténation d'une entrée client dans un chemin de fichier.
Correction: ne pas commiter. Si le besoin est réel, valider
            Number.isInteger(index) && index >= 0 && index < 1000, borner
            la taille du buffer, ne jamais concaténer dans un chemin, et
            authentifier. Périmètre : backend-api.

Problème  : les quatre autres défis envoient la tentative BRUTE ({move},
            {guess}, {order}, {value}) que le serveur évalue seul. Ces
            deux-là envoient succeeded: boolean, et le serveur fait
            littéralement : return { succeeded: attempt.succeeded === true }.
            gauge calcule Math.abs(pct-50) <= tolerancePct dans le
            navigateur ; reflex calcule reactionMs <= durationMs de même.
Scénario  : rejouer la server action avec {gameType:"gauge",
            succeeded:true} après le délai plancher. Seule barrière :
            isSkillAttemptTimingPlausible, qui mesure depuis l'ÉMISSION DU
            JETON (iat) et non depuis le geste — le code le documente
            lui-même comme limite assumée (ADR-031, skill.ts:176-182).
Impact    : à borner honnêtement. Le joueur ne choisit PAS quel lot il
            gagne : le succès ouvre un perform_atomic_spin normal,

            c'est UN TIRAGE À LA PLACE D'UNE PERTE FORCÉE, à chaque
            fenêtre. Sur une campagne à lots réels, c'est une fuite
            d'économie continue, et la porte de compétence vendue au
            commerçant ne tient pas.
Cause     : le serveur ne possède aucune graine du geste, donc rien à
            vérifier. C'est architectural, pas une omission.
Correction: rendre le geste déterministe côté serveur.
            - gauge : semer le balayage depuis le jeton (position =
              f(seed, t)), faire renvoyer l'horodatage d'arrêt, recalculer
              la position serveur.
            - reflex : faire émettre l'instant d'armement PAR LE SERVEUR
              (dans le jeton signé) au lieu du Math.random() local, puis
              vérifier reactionMs = t_reponse - t_armement_serveur.
            Le ressenti de jeu ne change pas. Périmètre : backend-api +

H2 — UNE RPC DE CAISSE TIRE SON AUTORISATION D'UN PARAMÈTRE APPELANT
-------------------------------------------------------------------------
Fichier   : supabase/migrations/20261028120000_ticket_or.sql:455-487
            grant : même fichier, l.538                [LU] CONFIRMÉ
Zone      : public.redeem_ticket_or(uuid, text, text)
Problème  : la fonction est security definer et « grant execute ... to
            authenticated ». Elle vérifie l'appartenance ainsi :
              select 1 from public.organization_members om
               where om.organization_id = p_organization_id
                 and om.user_id = v_actor      -- v_actor := p_actor::uuid
                 and om.role in ('owner','editor','cashier')

            occurrence dans tout supabase/migrations).
            Contraste dans le MÊME fichier : emettre_ticket_or (l.243)
            utilise public.is_org_member(), donc auth.uid(). Le routeur de
            référence redeem_reward_by_code (20260805150000:709) exige
            auth.role() = 'service_role' et ne traite p_actor que comme
            libellé d'audit.

            forme (organisation, code, acteur) grantée à authenticated.
            Le défaut est isolé, ce n'est pas une famille.

            p_organization_id = org B et p_actor = UUID d'un membre de B,
            et consomme les Ticket d'Or de B. L'org-scoping est respecté ;
            c'est l'IDENTITÉ qui ne l'est pas.
Exploitab.: à dire franchement — l'attaquant a besoin de DEUX valeurs
            qu'il n'a pas : un user_id de membre de la cible ET un code de
            retrait valide. La probabilité est faible aujourd'hui. Mais
            c'est une primitive d'autorisation cassée dans un produit
            multi-tenant : elle devient exploitable le jour où un user_id
            fuit (export, ticket de support, future page d'équipe).
Impact    : consommation de lots d'un autre commerçant.
Cause     : recopie de la FORME des neuf autres redeem_* (organisation,
            code, acteur) sans recopier leur GARDE (service_role).
Correction: la fonction n'est appelée depuis AUCUN fichier de src/ — elle
            n'apparaît que dans src/types/database.generated.ts ; le
            chemin vivant passe par le routeur universel
            (20261028120000:560). Le grant à authenticated est donc à la
            fois INUTILE et exploitable.
            Correction minimale, une ligne : remplacer le grant par
            « to service_role » seul.
            Correction de fond : dériver l'acteur de auth.uid().
            Périmètre : db-supabase, puis security-review.

=========================================================================

Consigné parce que l'absence de défaut est une information, et qu'elle
évite de réauditer la même surface au prochain tour.

  - Signature Stripe : constructEvent avec le vrai secret, corps lu en
    text() avant parsing, api/stripe hors matcher du proxy (le corps n'est
    jamais consommé en amont), idempotence à deux étages sur la bonne clé.
  - Comparaisons à temps constant : src/lib/timing-safe.ts est l'unique
    point du dépôt, longueurs comparées avant timingSafeEqual. Aucun ===
    sur un secret.
  - Secrets : aucun sk_live/whsec_/JWT en dur ; les 11 NEXT_PUBLIC_* sont
    tous légitimement publics ; SUPABASE_SERVICE_ROLE_KEY n'apparaît que
    dans src/lib/supabase/admin.ts sous import "server-only".
  - IDOR sur server actions : balayage des requêtes admin.* filtrées par
    id sans borne d'organisation — 28 résultats, TOUS avec un
    organization.id issu de la session ou une vérification d'appartenance.
  - Les 11 crons : garde unique fail-closed à temps constant sur l'en-tête
    ENTIER (préfixe « Bearer » compris), et idempotence RÉELLE sur chacun
    (clé jour+organisation, réservation email_log, for update +
    revalidation sous verrou pour le tirage jackpot, critère d'âge pour la
    purge). purge-data et jackpot-draws sont les mieux gardés du lot.

  - Turnstile : fail-closed en production ET sur erreur réseau, action et

  - redeem_by_code : UPDATE unique avec redeemed_at is null — un second
    retrait concurrent obtient 0 ligne. Scopé par organisation.
    L'expiration fait foi dans le WHERE.
  - Atomicité du stock : 6/6 des fonctions demandées protégées
    (decrement_prize_stock, restore_prize_stock, perform_atomic_spin,
    redeem_stock_hold, cancel_stock_hold, reserve_slot), plus les 12
